# AGENTS.md (Express Standalone)

This is a standalone Express 5 backend project.
This template adapts the backend architecture from `next-express` into a standalone service without Turborepo or `@workspace/*` packages.
Types and validation schemas live in local folders (`src/types/` and `src/validation/`).

> How to extend this file: add a new numbered section at the bottom, or a new numbered rule inside the matching section. Keep each rule short and actionable.

## 2. Repository Structure

```
│   ├── controllers/

│   ├── services/

│   │   └── <domain>.routes.ts     # one router per domain

│   ├── lib/

│   │   ├── errors.ts              # AppError class

│   │   └── response.ts            # success / error response helpers
│   ├── db/

│   │   ├── index.ts               # db instance (Pool + drizzle)

│   ├── types/

│   │   ├── auth.types.ts          # Session type

│   ├── tests/

│   ├── app.int.test.ts            # integration test of the whole app (supertest)

│   └── server.ts                  # Server entry point (listen on PORT)
├── Dockerfile
├── docker-compose.yaml
├── docker-compose.dev.yaml

├── oxlint.config.ts               # Oxlint linting configuration
├── package.json
├── tsconfig.json
├── tsup.config.ts
└── vitest.config.ts
```

2.1 Standalone mapping: There are **no** `@workspace/*` packages.

- Contract and app types live in `src/types/`.
- Zod schemas live in `src/validation/`.
  2.2 Linting is done with Oxlint (`oxlint --type-aware`). No ESLint.
  2.3 Formatting is done with Prettier.

## 3. TypeScript Rules

3.1 **Never use `any`.** Use proper types, generics, or `unknown` with narrowing.
3.2 Generic helper functions (`src/lib/response.ts`, `src/lib/nullToUndefined.ts`) require you to pass the proper type. Never leave them untyped.
3.3 Domain types go into `src/types/<domain>.types.ts` as flat files.
3.4 Because this project is Node ESM with TS bundler resolution, relative imports in TypeScript should end with `.js` when referencing sibling/relative modules or use the configured `@/*` path alias.

---

## 4. Validation

4.1 Zod is used for validation.
4.2 Schemas are always imported from `src/validation/` (e.g. `src/validation/<domain>.validation.ts`). Never define a schema inline in a controller or service.
4.3 Import the schema in the **controller** (see section 8).
4.4 Never write manual validation with `if/else` chains when a zod schema can do the job.

---

## 5. Code Quality (Global)

5.1 Keep logic separate. Every piece of logic gets its own function. Do not write business logic directly inside a controller or route.
5.2 Use clear, descriptive names for functions, queries, services, controllers, and middlewares.
5.3 Keep code simple, human-readable, scalable, maintainable, and clean.
5.4 Prefer small, single-purpose functions over long ones.
5.5 **No spaghetti code.** A function that does several things one after another is split: every distinct piece of logic becomes its own named function. Inside services, helper functions live in the same file below the main service function.
5.6 Auth logic (reading the session, checking roles, ownership checks, error mapping) is isolated in its own functions too.

## 6. Naming Conventions

| Kind              | Pattern                     | Example                       |
| ----------------- | --------------------------- | ----------------------------- |
| Controller        | `xY.controller.ts`          | `getProducts.controller.ts`   |
| Service           | `xY.service.ts`             | `getProducts.service.ts`      |
| Query             | `xY.query.ts`               | `getProducts.query.ts`        |
| Routes            | `xY.routes.ts`              | `product.routes.ts`           |
| Middleware        | `xY.middleware.ts`          | `auth.middleware.ts`          |
| Validation Schema | `xY.validation.ts`          | `product.validation.ts`       |
| Utils             | `xY.ts`                     | `formatPrice.ts`              |
| Types             | `xY.types.ts`               | `product.types.ts`            |
| Unit test         | `<source file>.test.ts`     | `createOrder.service.test.ts` |
| Integration test  | `<source file>.int.test.ts` | `app.int.test.ts`             |

(`xY` = camelCase.) A test file is named after the file it tests with `.test.ts` added.

## 7. Organization (Layers with Domain Sub-Folders, One Unit Per File)

7.1 **Layers:** `src/` has exactly one `controllers/`, one `services/`, one `queries/`, one `routes/`, and one `tests/` folder (plus `utils/` and `validation/` when needed). Do not create duplicate or extra top-level folders.
7.2 **One sub-folder per domain** inside `controllers/`, `services/`, `queries/`, `tests/`, and `utils/` (for example `test`, `products`, `orders`).
7.3 Use the **same domain name** in every layer: `controllers/test/`, `services/test/`, `queries/test/`, `routes/test.routes.ts`, `tests/test/`.
7.4 **Inside a domain folder, one file per unit:** one file per controller, one file per service, one file per query, one file per util.
7.5 **Never** put multiple controllers, services, queries, or utils in one file.
7.6 Private helper functions used only by one file go at the bottom of the same file (see section 15). A helper used by several files becomes its own util file in `utils/<domain>/`.
7.7 **Routes:** one router file per domain at `routes/<domain>.routes.ts`, and `routes/index.ts` mounts them all (section 9).

---

## 8. Request Flow

```
routes/index.ts -> routes/<domain>.routes.ts -> controller -> service -> query -> db
```

8.1 **Controller**: receives the request, validates body/params/query with zod, calls the service, and sends the result using `lib/response.ts`.
8.2 **Service**: business logic. Calls queries. Logic is broken into helper functions below the main function (no spaghetti code).
8.3 **Query**: the only layer that talks to the db instance. Uses `nullToUndefined` on rows so `null` never leaks out.
8.4 Controllers never touch the db directly. Queries never contain business logic.
8.5 Errors thrown anywhere are caught automatically by `errorHandler`. Always throw `AppError` from `src/lib/errors.ts`.

---

## 9. Routing

9.1 Each domain has one router file: `routes/<domain>.routes.ts`. It exports the router as **default**.
9.2 Domain routers are mounted in `routes/index.ts` with `router.use(path, ...middlewares, handler)`. Domain routers are loaded dynamically via `await import(...)`.
9.3 All API routes are under the `/api` prefix in `app.ts`. Auth routes are under `/api/auth`.

---

## 10. App Setup (app.ts and server.ts)

10.1 `app.ts` creates the Express application, configures middleware, and exports it as default (without calling `listen`). `server.ts` imports `dotenv/config` and calls `app.listen`.
10.2 The middleware order in `app.ts` is strict:

1. `cors` (origin from `process.env.CLIENT_URL`, `credentials: true`)
2. better-auth handler: `app.all("/api/auth/*splat", toNodeHandler(auth))`
3. `express.json()` (**after** better-auth handler)
4. `app.use("/api", router)`
5. `errorHandler`
6. `notFoundHandler`

---

## 11. Prebuilt Functions

11.1 `src/lib/response.ts`: `success` and `error` response helpers. **Never use raw `res.json`.**
11.2 `src/lib/errors.ts`: `AppError` class. **Always throw `AppError`, never the default `Error`.**
11.3 `src/lib/nullToUndefined.ts`: converts database `null` to `undefined`. Use it in query files.

---

## 12. Middlewares

12.1 Middlewares live in `src/middlewares/`: `auth`, `admin`, `error`, `notFound`.
12.2 `auth.middleware.ts` protects routes requiring authenticated sessions.
12.3 `admin.middleware.ts` protects routes requiring admin role.
12.4 `error.middleware.ts` and `notFound.middleware.ts` are registered in `app.ts`.

---

## 13. Database (Drizzle ORM v1)

13.1 Database: PostgreSQL via `node-postgres` with **Drizzle ORM v1**.
13.2 Schema in `src/db/schema.ts`, auth schema in `src/db/auth-schema.ts`, relations in `src/db/relations.ts`, instance in `src/db/index.ts`.
13.3 Migrations live in `src/db/migrations/` and are generated via `pnpm db:generate`.

---

## 14. Authentication

14.1 `better-auth` configured in `src/lib/auth.ts` using drizzle adapter and admin plugin.
14.2 `src/db/auth-schema.ts` is generated by `pnpm auth:generate`. Never edit manually.
14.3 Every piece of auth logic (session extraction, role checking, error mapping) is isolated in small helper functions.

---

## 15. Service Structure (No Spaghetti Code)

15.1 A service file has **one main exported function** (`xYService`) followed by helper functions in the **same file, below the main function**.
15.2 The main function reads like a table of contents / list of steps.
15.3 Every piece of logic (validation checks, data transformation, DB call) is its own helper.

## 16. Tooling & Commands

16.1 Package manager: **pnpm** (Node `>=24`). Strict TypeScript.
16.2 Linting: **Oxlint** (`oxlint --type-aware`). Prettier for formatting. Husky + lint-staged for pre-commit hooks.
16.3 Build: **tsup** (`pnpm build` outputs to `dist/server.js`). Dev: `tsx watch`.

| `pnpm lint`          | Run type-aware Oxlint                                      |

| `pnpm lint:ci`       | Oxlint with `--deny-warnings`                              |

| `pnpm format:check`  | Prettier check (read-only)                                 |

## 17. Self-Check Before Reporting a Task as Done

17.1 Are files in domain sub-folders (`controllers/<domain>/`, `services/<domain>/`, `queries/<domain>/`)?
17.2 Is there one unit per file with matching naming conventions?
17.3 Are service functions broken into small helpers below the main function?
17.4 Are zod schemas in `src/validation/` and imported in controllers?
17.5 Are `lib/response.ts`, `AppError`, and `nullToUndefined` used consistently?
17.6 Are there no `any` types and no raw `res.json` calls?
17.7 Do `pnpm lint`, `pnpm typecheck`, and `pnpm test:unit` pass cleanly?

## 18. Testing (Vitest + supertest)

18.1 Tests run with **Vitest** configured in `vitest.config.ts` with two projects: `unit` and `integration`.
18.2 Unit tests live in `src/tests/<domain>/` as `<unit>.test.ts`. Queries are mocked in service tests; services are mocked in controller tests.
18.3 Integration tests live in `src/app.int.test.ts` and `src/db/db.int.test.ts` using `supertest` against the exported `app`.
18.4 Tests are typed: no `any`. Use `vi.mocked(...)` for typed mocks.
