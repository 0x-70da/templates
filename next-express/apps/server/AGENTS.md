# AGENTS.md (apps/server)

Express backend. Read the root `AGENTS.md` first; this file adds server-specific rules.

> How to extend this file: add a new numbered section at the bottom, or a new numbered rule inside the matching section.

---

## 1. Stack

1.1 Express 5, TypeScript, ESM.
1.2 Database: PostgreSQL via `node-postgres` with **Drizzle ORM v1**.
1.3 Auth: `better-auth`. Auth routes and base URL live on this server.
1.4 Validation: zod.
1.5 Because the project is ESM, relative imports **must end with `.js`** (e.g. `import router from "./routes.js"`), even though the source files are `.ts`.
1.6 Tests: **Vitest** + **supertest** (section 16).
1.7 Build: **tsup** (`pnpm build` outputs `dist/server.js`). Dev: `tsx watch`.
1.8 Linting and formatting are done from the repo root (Oxlint + Prettier). This app has no lint script.

```
│   ├── db/

│   │   └── schema.ts

│   │   └── <feature>/
```

2.1 Everything of a feature lives in `features/<feature>/`.
2.2 The feature's **routes file** is `features/<feature>/<feature>.routes.ts` and the feature's **types file** is `features/<feature>/<feature>.types.ts`. They sit at the feature root, not in sub-folders.
2.3 Queries, services, and utils used by **more than 2 features** move to the matching root-level folder outside `features/`.
2.4 **Each feature has exactly ONE `controllers/` folder, ONE `services/` folder, ONE `queries/` folder, ONE `utils/` folder, and ONE `tests/` folder.** Do not create extra, nested, or per-entity folders for them (no `product-controllers/`, no `controllers/products/`, no `services/admin/`).
2.5 **Inside each of these folders, one file per unit:** one file per controller, one file per service, one file per query, and **one file per util**. The file is named after what the function does, and the function is exported with the matching suffix.
2.6 **Never** put multiple controllers, multiple services, multiple queries, or multiple utils in one file. These are all **wrong**: a `product.controller.ts` that contains `getProducts`, `createProduct`, and `deleteProduct` together; a `product.service.ts` or `product.query.ts` that groups all of them; a `utils/index.ts` or `utils/helpers.ts` that collects many utils.
2.7 Private helper functions used only by one file go at the bottom of the same file (see section 14). A helper used by several files becomes its own util file in `utils/`.
2.8 The same rules apply to the root-level shared folders (`queries/`, `services/`, `utils/` if one is created).
2.9 Tests: feature tests go in the feature's `tests/` folder. Global test setup and shared test helpers go in `src/test/`. See section 16.

## 3. Request Flow

```
routes.ts -> <feature>.routes.ts -> controller -> service -> query -> db
```

3.1 **Controller**: receives the request, validates any external data (body, params, query) with zod, calls the proper service, and sends the result using `lib/response.ts`.
3.2 **Service**: business logic. Calls queries. Every piece of logic is isolated in its own helper function at the bottom of the same file, below the main service function (see section 14). No spaghetti code.
3.3 **Query**: the only layer that talks to the db instance. Returns the data.
3.4 Controllers never touch the db directly. Queries never contain business logic.
3.5 Errors thrown anywhere are caught automatically by the error middleware. Do not wrap everything in try/catch just to format errors.
3.6 Every layer function lives in its own file (see 2.5). A controller imports exactly the service(s) it needs, and a service imports exactly the queries it needs.

## 4. Routing

4.1 Each feature has one router file: `features/<feature>/<feature>.routes.ts`. It creates a typed `Router`, attaches the controllers, and exports the router as **default**.
4.2 Controllers are **named exports** (`xController`) imported from `./controllers/x.controller.js`, one import per controller file.

```typescript
// features/products/products.routes.ts
import { Router } from "express";
import { getProductsController } from "./controllers/getProducts.controller.js";
import { createProductController } from "./controllers/createProduct.controller.js";

const router: Router = Router();

router.get("/", getProductsController);
router.post("/", createProductController);

export default router;
```

4.3 Every feature router is mounted in `src/routes.ts` with `router.use(path, ...middlewares, handler)`. The feature router is loaded with a dynamic `await import(...)` and its `.default`. Put the middlewares that protect the whole feature (auth, admin) in the mount call.

```typescript
// routes.ts
import { Router } from "express";
import { xMiddleware } from "./middlewares/x.middleware.js";

const router: Router = Router();

router.use(
  "/test",
  xMiddleware,
  (await import("./features/test/test.routes.js")).default,
);

export default router;
```

4.4 To add a new feature: create `features/<feature>/<feature>.routes.ts`, then add one `router.use(...)` block in `routes.ts` following the same pattern.
4.5 Use middlewares per route inside a feature router when only some routes need them (e.g. only `DELETE` needs `adminMiddleware`).

## 5. App Setup (app.ts and server.ts)

5.1 `app.ts` creates the express app, configures it, and **exports it as default**. `server.ts` only starts listening. Keep this separation.
5.2 The order in `app.ts` matters. Keep it exactly like this unless the owner approves a change:

1. `cors` (origin from `process.env.CLIENT_URL`, `credentials: true`)
2. better-auth handler: `app.all("/api/auth/*splat", toNodeHandler(auth))`
3. `express.json()` (**after** the better-auth handler, never before it)
4. `app.use("/api", router)`
5. `errorHandler`
6. `notFoundHandler`

```typescript
// app.ts
import express from "express";
import cors from "cors";
import router from "./routes.js";
import { errorHandler } from "./middlewares/error.middleware.js";
import { toNodeHandler } from "better-auth/node";
import { auth } from "./lib/auth.js";
import { notFoundHandler } from "./middlewares/notFound.middleware.js";

const app: express.Application = express();
app.use(
  cors({
    origin: process.env.CLIENT_URL,
    credentials: true,
  }),
);

app.all("/api/auth/*splat", toNodeHandler(auth));

app.use(express.json());

app.use("/api", router);

app.use(errorHandler);

app.use(notFoundHandler);

export default app;
```

5.3 `server.ts` imports `dotenv/config` **first**, then the app, then listens on `process.env.PORT || 5000`.

```typescript
// server.ts
import "dotenv/config";

import app from "./app.js";

const PORT = process.env.PORT || 5000;

app.listen(PORT, () => {
  console.log(`Server running on ${PORT}`);
});
```

5.4 Do not register `errorHandler` or `notFoundHandler` anywhere else. Do not add global middlewares in `app.ts` without notifying the owner.
5.5 All API routes are under the `/api` prefix. Auth routes are under `/api/auth`.

## 6. Prebuilt Functions (Always Use Them)

6.1 `lib/response.ts`: success and error response functions. **Never use raw `res.json`.** They are generic; pass the proper type.
6.2 `lib/errors.ts`: the `AppError` class (extends `Error`). **Always throw `AppError`, never the default `Error`.**
6.3 `lib/nullToUndefined.ts`: converts `null` to `undefined`. **Use it in query files** on database results so `null` never leaks out of the query layer.

---

## 7. Middlewares

7.1 Located in `src/middlewares/`: `admin`, `auth`, `error`, `notFound`.
7.2 Use `auth.middleware` on routes that require an authenticated user.
7.3 Use `admin.middleware` on routes that require admin permission.
7.4 `error` and `notFound` middlewares are already registered in `app.ts`. They catch errors thrown from controllers and unknown paths, so do not add them again.
7.5 One middleware per file (`xY.middleware.ts`). Middleware logic (especially auth and admin checks) is split into helper functions, see 10.4 and 10.5.

---

## 8. Validation

8.1 Zod schemas come from `@workspace/validation`. Never define them locally.
8.2 Import the schema in the **controller**.
8.3 Validate every piece of external data (body, params, query) in the controller before passing it to the service.
8.4 If a needed schema does not exist, create it in `@workspace/validation` (the client uses it too).

## 9. Database (Drizzle ORM v1)

9.1 The project uses the latest Drizzle ORM (**v1**). The API changed from older versions, so check the official v1 docs before writing queries; do not rely on old patterns.
9.2 Relations are defined in a **separate file** (`db/relations.ts`).
9.3 Schema in `db/schema.ts`, auth schema in `db/auth-schema.ts`, db instance in `db/index.ts`, migrations in `db/migrations/`.
9.4 Only query files import the db instance.

## 10. Authentication

10.1 `better-auth` is configured in `lib/auth.ts` and mounted in `app.ts` (see 5.2).
10.2 Check the better-auth docs for anything not covered here.
10.3 `db/auth-schema.ts` is generated (see section 13). Never edit it by hand.
10.4 **Every piece of auth-related logic gets its own function.** This includes: reading the session from the request, checking that a user is logged in, checking the user's role, checking ownership of a resource, mapping the session user to the app's user type, and mapping auth errors to `AppError`. Never write these steps inline in a middleware, controller, or service body.
10.5 In `auth.middleware.ts` and `admin.middleware.ts`, the exported middleware only orchestrates (get session -> verify -> attach to the request -> `next()`). Each step is a helper function at the bottom of the same file. If a helper is needed by other files, move it to its own util file.
10.6 Do not call `auth.api.*` directly from controllers. Wrap each call in a small named function (for example `getSessionFromRequest`) and call that function instead.
10.7 Agents often forget these rules for auth code. Before finishing, re-read every auth-related function you wrote and confirm each piece of logic is isolated.

```typescript
// middlewares/auth.middleware.ts (illustrative, follow the real types and AppError signature)
```

## 14. Service Structure (No Spaghetti Code)

14.1 A service file has **one main exported function** (`xYService`) followed by the helper functions it uses, in the **same file, below the main function**.
14.2 The main service function must read like a short list of steps. It calls helper functions and passes data between them. It does **not** contain loops, `if` chains, mapping, calculations, or checks written inline one after another.
14.3 **Every piece of logic is its own helper function**: validating a business rule, checking existence, calculating a value, mapping data, building a payload, calling a query, and so on. One helper does one thing.
14.4 Name helpers by what they do, with a verb (`calculateOrderTotal`, `assertStockAvailable`, `mapOrderToResponse`).
14.5 Helpers are not exported unless another file needs them. A helper needed by several files moves to its own file in `utils/` (or the root-level shared folder if used by more than 2 features).
14.6 Helpers are typed explicitly (parameters and return type). Never use `any`.
14.7 The same idea applies to controllers, middlewares, and queries: if a function grows into several steps, extract each step into a named helper at the bottom of the file.
14.8 Wrong: one long service function with all the logic written line after line. Right: a short main function plus helpers below it.

```typescript
// features/orders/services/createOrder.service.ts (illustrative)
import type { CreateOrderInput, Order, Product } from "@workspace/types";
import { AppError } from "../../../lib/errors.js";
import { getProductsByIdsQuery } from "../queries/getProductsByIds.query.js";
import { createOrderQuery } from "../queries/createOrder.query.js";

export async function createOrderService(
  userId: string,
  input: CreateOrderInput,
): Promise<Order> {
  const products = await getExistingProducts(input);

  assertStockAvailable(products, input);

  const totalPrice = calculateOrderTotal(products, input);

  return createOrderQuery({ userId, totalPrice, items: input.items });
}

async function getExistingProducts(input: CreateOrderInput): Promise<Product[]> {
  const ids = input.items.map((item) => item.productId);
  const products = await getProductsByIdsQuery(ids);

  if (products.length !== ids.length) {
    throw new AppError("Some products were not found", 404);
  }

  return products;
}

function assertStockAvailable(products: Product[], input: CreateOrderInput): void {
  /* throw AppError if any item quantity exceeds stock */
}

function calculateOrderTotal(products: Product[], input: CreateOrderInput): number {
  /* sum price * quantity for each item */
  return 0;
}
```

## 16. Testing (Vitest + supertest)

16.1 `vitest.config.ts` defines two projects: **`unit`** (files `*.test.ts`) and **`integration`** (files `*.int.test.ts`). Do not change the Vitest config without notifying the owner.
16.2 **Feature unit tests** live in the feature's single `tests/` folder (`features/<feature>/tests/`). Name each file after the file it tests: `createOrder.service.ts` -> `createOrder.service.test.ts`. **One test file per unit** (per controller, service, util, middleware), not one big file.
16.3 **The global folder `src/test/`** holds the global setup (`global-setup.ts`, `setup.ts`) and shared test helpers. Read these files before writing tests and do not change them without notifying the owner. Put tests for shared root-level code (root `queries/`, `services/`) here as well. Do not put feature tests here.
16.4 What to unit test:

- **Services:** mock the queries (`vi.mock`) and test the behavior through the exported service function: the success path, every business-rule failure, and the `AppError` thrown. Do not test private helpers directly.
- **Controllers:** mock the service. Check zod validation failures, the status code, and the response shape produced through `lib/response.ts`.
- **Utils:** pure input/output tests, including edge cases.
- **Middlewares (especially `auth` and `admin`):** mock `req`, `res`, and `next`. Check allowed and rejected cases.
- **Queries:** do not unit test them by mocking the db (it proves nothing). Cover them with integration tests against the real test database.

16.5 **Integration tests** (`*.int.test.ts`) use `supertest` against the `app` exported from `app.ts`. Never call `listen` in tests. They use the real test database prepared by the global setup and cover the full flow (route -> middleware -> controller -> service -> query), auth/admin protection, validation errors, and the error and not-found responses.
16.6 Integration tests live next to what they cover, like `src/app.int.test.ts` and `src/db/db.int.test.ts`. For a feature's HTTP flow, add `<name>.int.test.ts` in the feature's `tests/` folder.
16.7 Unit tests must never touch the real database or the network. Integration tests must only use the test database from the setup, never any other data.
16.8 Tests are typed: no `any`. Use `vi.mocked(...)` for typed mocks, and reset mocks between tests (`vi.clearAllMocks()` or the config's restore options).
16.9 Structure: one `describe` per unit, one `it` per behavior with a clear name, Arrange-Act-Assert, and independent tests with no shared mutable state.
16.10 If there is no existing helper to create an authenticated user or session in integration tests, ask the owner before inventing one.
16.11 Never delete, skip (`it.skip`), or weaken a test to make it pass. Never leave `.only`.

```typescript
// features/orders/tests/createOrder.service.test.ts (illustrative)
import { beforeEach, describe, expect, it, vi } from "vitest";
import { createOrderService } from "../services/createOrder.service.js";
import { getProductsByIdsQuery } from "../queries/getProductsByIds.query.js";

vi.mock("../queries/getProductsByIds.query.js");

describe("createOrderService", () => {
  beforeEach(() => {
    vi.clearAllMocks();
  });

  it("throws when a product does not exist", async () => {
    vi.mocked(getProductsByIdsQuery).mockResolvedValue([]);

    await expect(
      createOrderService("user-1", { items: [{ productId: "p1", quantity: 1 }] }),
    ).rejects.toThrow();
  });
});
```
